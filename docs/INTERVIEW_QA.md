# 实现细节问答（面试准备）

按面试官最可能的提问路径整理，答案都指向代码里的真实实现。文件位置：`app/*.py`。

## 一、需求理解

**Q1：题目说"接收探测任务，后台探测，返回结果"，为什么做成异步任务 + 轮询，而不是同步接口？**
探测的耗时由目标决定（不可达目标要等满超时，批量时更久），同步接口会把 HTTP 连接拖到几十秒，容易被网关超时截断、也占满 worker。异步任务模型：提交立即返回 202 + 任务 id，后台协程执行，客户端轮询；另外给出 `wait=true` 长轮询作为便利糖（内部等一个 `asyncio.Event`，最多等 `wait_timeout_ms`），手工验证时体验最好。

**Q2：批量里有一个目标失败，任务算什么状态？**
任务仍然是 `succeeded`。`timeout`、`closed`、`dns_error` 都是**有效探测结果**，不是任务失败。任务级 `failed` 只用于编排层未预期异常（防御性分支，正常不应出现）。每个目标自己的状态在 `results[i].status` 里。

**Q3：为什么要把 `closed` 和 `timeout` 分开？**
语义完全不同：`closed` 是对端回了 RST——主机可达、包到了、端口明确拒绝；`timeout` 是预算内什么都没收到，什么也证明不了（可能是防火墙静默丢包，也可能是主机宕机）。对使用方来说，一个说明"服务没启动"，一个说明"路径不通/不确定"，处置动作不同。

**Q4：`invalid` 在 API 层已经 422 拦掉了，prober 里为什么还判一次？**
防御性设计：`probe_tcp` 是独立的引擎函数，未来可能被其他入口（CLI、内部调用）复用，不能假设调用方已经校验过。第二道防线放在引擎入口，成本是几行代码。正常 HTTP 请求在 Pydantic 层就被拒了，不会走到这里。

**Q5：为什么按来源 IP 限流，而不是按任务/按 key？**
作业要求"简单的限流"，服务没有身份体系，来源 IP 是唯一现成的维度；按任务限流粒度太粗（一次突发就耗尽）。若未来加鉴权，限流键可以切换为 API Key（令牌桶实现不变，只换 key 来源）。

## 二、架构与并发

**Q6：为什么选 FastAPI？分层是怎么想的？**
FastAPI 自带 Pydantic 校验与 OpenAPI 文档，团队普及率高。分层是"协议 / 编排 / 引擎 / 存储"四层：`api.py` 只做 HTTP 协议转换与错误映射；`service.py` 管任务生命周期（提交、并发、取消、背压）；`prober.py` 是纯函数式探测引擎；`store.py` 管内存治理。好处：prober 可单独单测（不需要 HTTP），store 可整体替换为 Redis。

**Q7：为什么是单事件循环 + 协程，不用线程池/多进程？**
探测是纯 IO 等待（等 SYN-ACK/RST/超时），协程切换成本远低于线程；单线程还消除了任务状态的并发写问题（不需要锁）。真正的并发上限由"在途 TCP 连接数"决定，用全局 `asyncio.Semaphore` 控制（默认 100），与事件循环的协程数无关。

**Q8：`Task` 会被多个协程写，为什么不用锁？**
所有写入都在同一个事件循环线程里：`_run_one` 写 `results[i]`、`completed += 1`，都是协程里同步执行的普通赋值，事件循环的协作式调度保证它们不会真正并行；不存在跨线程写。唯一的"交错"是 `await` 点之间的调度，而每次写入本身是原子的（单个 Python 字节码级别赋值 + 列表槽位写）。

**Q9：全局信号量控制的是什么？为什么不是限制任务数？**
控制的是**同时在途的 TCP 连接数**——这是要保护的真实资源（文件描述符、本机端口、出口带宽）。限制任务数不能防止"1 个任务 200 个目标"瞬间打出 200 个连接。任务数限制另有 `TASK_MAX_ACTIVE`（背压），两者职责不同。

**Q10：结果列表为什么要固定长度 + null 占位，而不是 append？**
顺序语义：结果必须与提交顺序一一对应，调用方才能按下标对应目标。并发完成顺序天然乱序，append 会乱序；固定长度数组让每个探测协程只写自己的槽位 `results[i]`，无需排序、无需锁；`null` 表示"尚未完成"，查询中间状态时语义清晰。

**Q11：取消是怎么实现的？**
`DELETE` → `service.cancel()`：对协调协程 `asyncio.Task.cancel()` → `gather` 传播取消到所有在途探测协程 → `_run` 捕获 `CancelledError`，把仍是 `null` 的槽位补成 `cancelled`（已出的结果保留）→ 任务置 `CANCELLED` 终态 → 重新抛出 `CancelledError`（保留取消语义）→ `cancel()` 外层收敛。关键点：prober 里有明确注释，**绝不吞 `CancelledError`**。

**Q12：进程关停时在途任务怎么办？**
FastAPI 的 lifespan 在 shutdown 阶段调用 `service.shutdown()`：取消所有在途任务并 `gather(return_exceptions=True)` 等它们完成清理（槽位补齐、`finished_at` 落值），然后进程退出。uvicorn 的 graceful shutdown 给了这个清理窗口。

**Q13：单实例内存存储，重启就丢，你怎么看？**
作业范围是单实例服务，内存存储是最小完整实现；接口已经隔离在 `TaskStore`（add/get/list/count_active），替换成 Redis 不影响上层。README「已知限制」明确写了。多实例时还需要把"任务调度"本身也外移（队列 + worker），这在 DESIGN 的改进路线里。

## 三、探测语义

**Q14：`timeout_ms` 的预算怎么分配？为什么要共享 deadline？**
`timeout_ms` 是单个目标的**总预算**：DNS 解析 + 最多 8 个候选地址的每次 `connect` 共享同一个 deadline（`time.monotonic()` 计时）。每次尝试的超时 = 剩余预算。这样"一个目标最多花 timeout_ms"对调用方是确定性的；如果每次尝试各自给满 timeout，一个域名解析出 4 个地址就会最坏花 4 倍时间。

**Q15：DNS 解析怎么做超时？有什么坑？**
`loop.getaddrinfo` 在 executor 线程中执行，外层用 `asyncio.wait_for` 包剩余预算。坑：`wait_for` 超时只是取消"等待者"，executor 里的 `getaddrinfo` 线程要等系统解析返回才能释放——一次探测最多一个解析线程，受全局信号量约束，不会无限增长。这是 Python 标准库的固有限制，文档已写明；生产化可换异步 DNS 库。

**Q16：`latency_ms` 计的是哪一段？**
只计**成功那一次 TCP 握手**的 `perf_counter` 差值，不含 DNS 解析、不含此前失败地址的耗时。语义单一、可横向对比。若要把 DNS 耗时也暴露，应作为独立字段而不是混进 latency。

**Q17：一个域名解析出多个地址（IPv4+IPv6）怎么处理？**
顺序尝试前 8 条 addrinfo，共享剩余预算；状态收敛优先级 `open > closed > timeout > unreachable`。限制 8 条是防御性上限（正常情况下 A/AAAA 记录远少于 8）。未实现 Happy Eyeballs（RFC 8305）的并发首包，文档列为改进项。

**Q18：`closed` 为什么优先级高于 `timeout`？**
RST 是确定性证据：包到了主机、端口没监听。多地址场景下，只要任一地址明确拒绝，就说明该端口在某条可达路径上未监听；其余地址的静默超时不构成反证。反过来如果先按 timeout 收敛，就把已经拿到的确定信息丢了。

**Q19：机器上没有 IPv6 或 DNS 很慢，结果会怎样？**
DNS 慢：在预算内等，超预算按 timeout/ dns_error 收敛（区分：`gaierror` 是明确解析失败 → `dns_error`；等待超时 → `timeout`）。无 IPv6：`getaddrinfo` 返回的 v6 地址连接会快速失败（网络不可达），继续尝试 v4 地址，最终不影响 v4 可达的结论。

## 四、限流

**Q20：为什么用令牌桶？和固定窗口、漏桶的区别？**
固定窗口有临界双倍突发问题；漏桶适合"整形"（强制匀速），不适合"限流"（允许突发）。令牌桶允许不超过 burst 的瞬时突发、长期速率不超过 rps，正好匹配"接口限流"语义；实现只需要 tokens + last_refill 两个变量加浮点运算。

**Q21：`Retry-After` 怎么算的？**
`ceil((1 - tokens) / rps)`，至少 1 秒。`(1 - tokens)` 是还差多少令牌才够一次请求，除以补充速率就是等待秒数；HTTP 头要求整数秒，所以向上取整。

**Q22：限流为什么放 ASGI 中间件而不是路由函数里？**
横切关注点：所有 `/api/*` 统一生效，路由无需感知；而且中间件可以在不解析 body 的情况下快速拒绝，省掉 JSON 反序列化的成本。`/healthz` 与 `/` 被排除，保证探针永远可用。

**Q23：为什么不信任 `X-Forwarded-For`？**
该头可由客户端任意伪造；只有经过可信代理清洗后才有效。当前实现取 `scope["client"]` 的 TCP 对端地址——如果前面有反向代理，所有请求的 key 都会是代理 IP，限流退化为全局限流。正确做法是代理层做真实来源限流，或在配置中显式声明信任代理（避免"半吊子信任"）。

**Q24：大量伪造来源 IP 会不会把限流器内存打爆？**
会，所以有内存治理：每个 key 一个桶 + `last_seen`，每 1024 次检查或桶数超过 4096 时触发惰性清扫，回收空闲超过 `idle_ttl_seconds`（默认 600s）的桶。攻击窗口内内存上限是"600 秒内的独立 key 数"，不会无限增长。

## 五、存储与工程

**Q25：TTL 和容量淘汰为什么用"惰性清理"而不是定时任务？**
任务条数被 `TASK_MAX_RETAINED`（默认 1000）限制，每次 `add/get/list` 全表扫描的成本可忽略（O(n), n≤1000）；惰性清理没有额外线程/定时器，实现简单、行为可预测。真到十万级任务时会换 Redis 的 TTL 或后台清扫任务。

**Q26：为什么错误响应要统一信封？**
调用方只需处理一种错误形状：`{"error": {code, message, request_id, details}}`。HTTP 状态码表达大类（4xx/5xx），`code` 表达具体业务原因（`TARGETS_TOO_MANY` 等），两者组合让脚本和人都好处理。框架层异常（422/404/405）也通过 `@app.exception_handler` 转成同一形状，避免 FastAPI 默认 `{"detail": ...}` 和业务错误两种风格并存。

**Q27：`X-Request-ID` 怎么贯穿？**
`RequestContextMiddleware`（最外层）优先透传调用方的合法 id（≤64 字符、限定字符集），否则生成 uuid4；存入 `ContextVar`，响应头回写；JSON 日志 formatter 自动带 `request_id` 字段；错误信封里也带上。排障时一条 request id 串起访问日志、业务日志和客户端看到的响应。

**Q28：测试怎么做到不依赖外网还覆盖所有状态？**
- `open`：本机 `listen` 一个端口（不 `accept`，内核会完成握手）；
- `closed`：绑定端口后立即关闭，连接得到 RST；
- `dns_error`：RFC 2606 保留 TLD `.invalid`，保证 NXDOMAIN；
- `timeout`：monkeypatch 模块级 `_connect_once` 抛 `TimeoutError`，确定性构造；
- 限流/存储：注入假时钟，数学可直接断言；
- 编排层：探测函数整体打桩，只验证顺序/取消/背压语义。
全部用 pytest，测试函数是同步 `def` + `asyncio.run()`，不依赖 pytest-asyncio 插件。

**Q29：配置为什么用环境变量而不是配置文件？**
12-factor：容器/CI/K8s 注入最方便，密钥不进仓库；所有配置集中在 `Settings` 一个 frozen dataclass，启动时校验（非法值直接报错退出），避免"带病运行"。`.env.example` 是文档，服务本身不读 `.env`（避免隐式魔法）。

**Q30：如果再给一周，你会改什么？**
优先级：① 鉴权 + 目标白名单（当前服务可被滥用做 SSRF/扫描）；② Redis 存储 + 队列实现多实例；③ Prometheus 指标（任务计数、探测耗时直方图、限流命中）；④ Happy Eyeballs 探测优化；⑤ 请求体大小限制与 per-tenant 配额。
